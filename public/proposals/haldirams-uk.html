01Our Understanding
From in-house DHL to Sipup's dark stores.

Haldiram's UK currently fulfils all Shopify orders in-house — picked, packed and dispatched via DHL from your own warehouse. You're transitioning fulfilment to Sipup, whose network of 7–8 dark-store warehouses across London opens the door to rapid delivery.

Phase 1 — Business-critical

Automatically route every Shopify order to Sipup, with acknowledgement, inventory, tracking and status flowing back into Shopify — no interruption to trading, no visible change for customers.

Phase 2 — Rapid delivery

Launch 60-minute and 90-minute delivery across London: postcode-based eligibility, dynamic delivery pricing, and automatic routing of each order to the nearest Sipup warehouse.

Everything is architected to extend to chilled/frozen ranges and geographies beyond London without a rebuild.

02Recommended Architecture
A private app that owns the wiring.

We recommend a dedicated integration layer built as a private Shopify app — a lightweight, cloud-hosted service that sits between Shopify and Sipup and owns all communication between the two. Sipup runs its own dark-store technology rather than an off-the-shelf 3PL platform, so a purpose-built layer is the most reliable path: full control over routing, retries, error handling and logging — and it becomes the same engine that powers Phase 2's multi-warehouse routing.

Why not a plug-and-play connector?

Off-the-shelf iPaaS tools (Patchworks, Alloy, Zapier-class) assume the 3PL runs a supported platform. They add monthly licensing, and none of them can express Phase 2's postcode-to-warehouse routing logic. A private app has no per-month platform fee, is owned by you, and handles both phases in one codebase.

Every order, routed and tracked.

Shopify fires a paid-order webhook to the integration layer within seconds. The order enters a persistent queue — nothing is lost, even if Sipup is momentarily unreachable.

The order is mapped to Sipup's format (SKUs, quantities, address, delivery notes) and pushed to Sipup's order API.

04

Sipup's confirmation is recorded. If none arrives in a defined window, the push retries automatically with escalating delays; persistent failures raise an alert.

05

Fulfilled

Sipup picks, packs and hands the parcel to their courier network.

06

Tracking synced

Dispatch event, courier and tracking number are written back to Shopify via the Fulfillment API — order marked fulfilled, Shopify's own email goes out, exactly as today.

07

Delivered

Further status events (out for delivery, delivered) update the order timeline in Shopify.

Inventory synchronisation

Sipup's warehouse becomes a fulfilment location in Shopify. Stock levels sync from Sipup on a schedule (typically every 10–15 minutes, or real time if Sipup supports stock webhooks), so the storefront never oversells and never blocks a sale on stale data. During cutover we reconcile your current stock file against Sipup's intake count before switching.

Error handling, alerts & reporting
  • Classified failures — every failure mode is classified: unreachable API, rejected order, unknown SKU, address-validation failure, partial stock.
  • Instant notifications — failed orders alert your team by email (and Slack/WhatsApp if preferred) immediately, with a plain-language reason and a one-click retry.
  • Reconciliation view — a simple ops dashboard lists every order's journey (received → pushed → acknowledged → dispatched), so daily reconciliation takes minutes, not spreadsheets.
What we need from Sipup

The exact wiring depends on what Sipup's system exposes — a discovery question, not a project risk. We've designed for whichever applies: if Sipup has an API (or a WMS with connectors), we integrate directly and in real time. If no API is available yet, an interim automated file exchange keeps orders flowing from day one, and we upgrade to real-time once Sipup's endpoints are ready. Either way, go-live is unaffected.

Seamless cutover — zero interruption
  • Full workflow rehearsed with test orders in a sandbox against Sipup's system.
  • Parallel run — live orders route to Sipup while your warehouse remains on standby as fallback.
  • Cutover during a low-traffic window; the DHL process is retired only once the Sipup flow is verified on real orders.
04Phase 2 — 60 & 90-Minute Delivery
Rapid delivery, routed by postcode.

Postcode eligibility checker

A postcode entry on the storefront (home and product pages) validates against UK postcode data, resolves to coordinates, and checks each Sipup warehouse's coverage zone. Eligible customers see "60 & 90-minute delivery available in your area"; others see standard messaging. Zones are configurable per warehouse — switch a new site on with no code change.

Dynamic delivery pricing

Using Shopify's Carrier Service API, checkout requests live rates from our pricing engine per order. It calculates fees from postcode, distance and zone relative to the serving warehouse, returning Standard, 60-Minute and 90-Minute — each with its own charge. Pricing rules live in a config panel you control.

Warehouse allocation & routing

Locate the nearest covered warehouse → live stock-check every line item (fall through to next-nearest if short) → load-balance to cap orders per warehouse per window → route with the delivery deadline attached and flag rapid orders for priority picking.

Live order status

Customers get the same confirmation, dispatch, tracking and delivery updates built in Phase 1 — rapid orders simply move through faster, with courier tracking from Sipup's delivery network.

Built for what's next

Chilled & frozen — products carry a temperature-class attribute; routing automatically restricts chilled/frozen items to equipped warehouses. Beyond London — new cities are new zones and warehouses in configuration; the routing and pricing engine is location-agnostic.

06Shopify App & Third-Party Requirements
Owned by you, no per-order fees.
  • Shopify apps — one private custom app (the integration layer). No public app-store apps, no per-order fees, and the code is owned by Haldiram's UK.
  • Third-party software — cloud hosting for the integration service and its database (a modest footprint, billed at cost — typically a small monthly infrastructure charge). UK postcode lookup uses open data at no licence cost.

07Testing Approach
Proven before it touches a real order.
  • Component tests — every payload mapping and pricing rule is unit-tested before it touches an order.
  • End-to-end sandbox — full order lifecycle rehearsed against Sipup's sandbox (place → push → acknowledge → dispatch → track → notify), including deliberate failure injections (bad SKU, timeout, out-of-stock) to prove alerts fire.
  • UAT — structured scripts for your team and Sipup's: real test orders through the live store, verified at every checkpoint. Phase 2 adds postcode-matrix testing across zones, boundaries and ineligible areas.
  • Go-live verification — first live orders monitored order-by-order jointly with both teams.
08Deployment & Go-Live
Staged and reversible at every step.

Deployment is staged and reversible: sandbox first, then a parallel-run window with your warehouse on standby, then full cutover in a low-traffic window. Rollback is a single switch back to the current process — at no point is the store's ability to take and fulfil orders at risk. Phase 2 features ship behind flags: the postcode checker and rapid-delivery options are enabled zone by zone, so launch can start with one warehouse's catchment and expand smoothly.
